# Still-image resize production selection v2

- Status: selected for D3.5 production integration
- Date: 2026-08-13
- Contract: [`qwen-mm-still-image-resize-v2`](image-resize-contract-v2.md)

## Decision

Use `pic-scale=0.7.11` for still-image resizes that change at least one spatial
dimension. The selected configuration is:

- `ResamplingFunction::Bicubic`;
- `WorkloadStrategy::PreferQuality`;
- `ThreadingPolicy::Single`; and
- `default-features=false` with the runtime-dispatched `neon`, `rdm`, `sse`,
  and `avx` implementation features.

The caller's validated positive-stride RGB8 view is borrowed directly by
`ImageStore`; padded rows are not packed first. The destination and the exact
scratch size requested by the per-call plan are allocated fallibly by
qwen-mm. Plans and scratch are not cached. Batch-level image parallelism
remains the only production threading layer, so the resizer cannot create a
nested thread pool or oversubscribe the processor budget.

An exact no-op never enters pic-scale. It keeps qwen-mm's checked row-copy,
including byte-exact handling of padded source rows. Video remains on the
source-faithful TorchVision-compatible implementation recorded in
[`resize-parity-v1`](resize-parity-v1.md).

## Selection evidence

The candidate-blind 45-case holdout and all thresholds were frozen before
pic-scale output was inspected. The authenticated report
[`macos-arm64-pic-scale-bicubic-prefer-quality.json`](../reference/resize/v2/results/macos-arm64-pic-scale-bicubic-prefer-quality.json)
passes every per-occurrence/per-channel v2 gate, exact invariant, and the
cross-case channel-permutation check. Its observed worst per-channel values
were max error 30, RMSE 3.59623, p99 error 14, absolute bias 0.70833, and SSIM
0.993704.

On the local M4 setup-inclusive comparison across the 12 cases that actually
resize, Bicubic/PreferQuality measured a 5.50x geometric-mean speedup over the
former scalar Pillow port and won every case. This is candidate-selection
evidence, not the controlled ARM/x86 end-to-end release certification required
by D4.

The faster default `PreferSpeed` strategy was rejected because it violated the
exact constant-RGB invariant on an extreme anisotropic case. FIR Catmull-Rom
passed the quality gates but measured only a 2.81x geometric-mean improvement
over the scalar port. Pic-scale Catmull-Rom/PreferQuality also passed and was
close in speed, but Bicubic had slightly lower aggregate error and the higher
measured integration speed.

## Errors and observability

All qwen-mm plan and source validation still runs in its original deterministic
order before the dependency is called. Pic-scale out-of-memory and
source/destination capability failures map to `resource_limit`; any other
pic-scale rejection after qwen-mm validation maps to `internal_invariant` with
the dependency error code and detail.

Observed calls count and reconcile the qwen-mm-owned destination and scratch
buffers supplied to pic-scale. Pic-scale does not expose the byte capacity of
its internal filter weights, so those per-call plan allocations are disclosed
as profile-only and are not presented as exact allocation counters.

Pic-scale 0.7.11 also does not expose a fallible allocator for those internal
plan weights. Qwen-mm's checked geometry and prepared-image caps bound their
size before plan construction, and all destination and scratch allocations
owned by qwen-mm remain fallible, but an allocator-level failure while the
dependency constructs the bounded plan cannot currently be translated into a
qwen-mm `resource_limit` error. This is an explicit dependency limitation, not
a claim that every allocation in the selected library is recoverable.

## Historical implementation

The former source-faithful Pillow scalar kernel is compiled only in core tests
to keep the authenticated v1 historical oracle check meaningful. It is not
linked into normal qwen-mm consumers and is not reachable from the production
still-image path.

The post-selection Rust diagnostics name the public qwen-mm backend
`selected-production` (quality-v2 blob generator) or
`qwen-mm-selected-production` (timing bake-off). They do not reuse the former
`scalar` label. Historical scalar measurements remain in the committed
selection reports and ticket worklog rather than being silently regenerated by
the current production entry point.
