# Integrate still-image qwen-mm preprocessing with a vLLM server

## Goal

Make qwen-mm useful in a real still-image vLLM serving workload with the least
possible deployment change. Prefer an official prebuilt vLLM wheel/container
and a supported request interface; next preference is an installable external
Python plugin. Prove that native CPU preprocessing happens once, the vision
encoder still runs in vLLM, and the complete serving path has a measured benefit.

The King selected this as the next work before a public launch, without waiting
for video. His preferred arrangement is caller-side preprocessing followed by
submission to a vLLM server that skips the corresponding preprocessing. Treat
that as the first interface to test, not an already-proven server capability.

## Existing evidence and the flag distinction

- `f7f4` is the closed A6 seam spike, not the completed production integration.
  `docs/vllm-prepared-pixel-seam.md` and `integrations/vllm/` prove an external
  general plugin with a custom parser/processor at vLLM v0.23.0, commit
  `0fc695fc6d1d82e9a5ac6835ac8e4e1c83703665`. It accepts pre-encoder
  `pixel_values`, `image_grid_thw`, final prompt IDs, and cache/range metadata
  without an upstream source patch. The old empty-device source build was a
  Mac development test, not a requirement for production installation.
- A6 proves the Python engine input boundary. It does not establish that stock
  OpenAI HTTP request parsing transports arbitrary prepared-pixel dictionaries.
  The server request schema and engine plugin are separate parts of this work.
- Upstream v0.28.0 documentation checked on 2026-09-05 describes
  `--enable-mm-embeds` and HTTP `image_embeds` as precomputed vision features.
  qwen-mm produces pre-encoder pixels, so relabeling its output as embeddings
  would incorrectly bypass the model's vision encoder.
- `--skip-tokenizer-init` concerns tokenizer/detokenizer initialization;
  `--skip-mm-profiling` concerns startup memory profiling. Neither establishes
  a prepared-image server input contract. `mm_processor_kwargs` passes
  processor options; it is not evidence of a complete preprocessing bypass.
- Final standalone release candidate `5746358` and
  `reference/releases/v0.1.0/README.md` provide verified ARM/Linux artifacts.
  Preserve that candidate and historical conformance/performance provenance.

## Scope and execution order

1. Pin a published vLLM binary release/container and its Qwen compatibility.
   Recheck the current supported interfaces against A6's older pin. Record the
   exact version, image/wheel identity, model revisions, and dependency set.
   Do not assume the documentation version is automatically the chosen pin.
2. Test the preferred stock-server path with a minimal executable HTTP request.
   Trace the request schema through media parsing, processor dispatch, prompt
   handling, and the model's pixel/embedding branches. Establish whether final
   prompt IDs and pre-encoder pixels/grids can actually enter this way. Capture
   the exact successful payload or the precise validation/semantic rejection.
3. If stock transport is insufficient, implement the smallest external adapter
   supported by the binary distribution, building on A6. Evaluate ordinary
   image requests with server-side qwen-mm processing versus a small prepared-
   input gateway around the public async engine. Explain which deployment
   changes are required; a Python-engine dictionary test cannot stand in for
   an HTTP-server test. Resolve the material placement/API choice with the King
   before committing to a different public workflow. If a source patch or
   custom vLLM build is actually necessary, present the concrete missing hook
   and alternatives first rather than starting that larger change silently.
4. Wire both pinned processor profiles and test text-only, one-image,
   unequal multi-image/interleaved, repeated-image, and concurrent requests.
   Preserve prompt tokens, grids, placeholder ranges, per-image identity,
   output-affecting options, error behavior, and cache cold/warm semantics.
   Run a real supported Qwen model through the actual server/client route;
   identify any profile covered by preprocessing only rather than inference.
5. Prove absence of duplicate CPU work with fail-fast spies or request-scoped
   counters. Verify that prepared pixels reach the vision tower and that the
   tower is not bypassed or invoked twice for an uncached image. Account for
   ownership snapshots, NumPy/Torch wrapping, tensor concatenation, transport,
   IPC, host-to-device transfer, and dtype conversion. Do not call the whole
   remote route zero-copy. Schedule CPU work off the serving event loop.
6. Compare the stock and integrated path on the same model, hardware, request
   corpus, thread/concurrency budgets, generation settings, and cache state.
   Include one-image and image-heavy/concurrent requests, separate cold and
   warm cache behavior, and record preprocess-to-submit, TTFT, throughput,
   event-loop stalls, failures, and memory. Include network serialization and
   payload bytes if preprocessing runs outside the server: expanded float32
   pixels can dwarf compressed images (the historical image24 fixture is
   about 432 MiB of pixels from about 6.1 MiB of JPEG data).
7. Retain an executable client example, exact server launch/install commands,
   correctness witnesses, raw measurements, and a readable adoption decision.
   If benefit is absent or transport erases it, report that outcome and the
   next concrete bottleneck; do not invent a passing threshold after measuring.

## Non-goals

Video/frame sampling, moving the vision encoder to the client, arbitrary model
support, a maintained vLLM fork, broad serving redesign, publication, and a new
strict D4/F3 production certificate are outside this ticket. A bounded serving
measurement does not relabel the historical D4 MISS or silently waive the
existing formal certification gates. The King subsequently authorized bounded Modal GPU testing; see the worklog.

## Acceptance Criteria

- [x] A version-pinned interface audit and executable request resolve the
      stock-server skip-preprocessing hypothesis, including the difference
      between pre-encoder pixels and post-encoder embeddings.
- [ ] The selected deployment uses a published vLLM binary wheel/container
      without source patches or a custom build, plus only the documented
      external adapter if needed; any unavoidable exception is explicitly
      resolved with the King rather than hidden in setup instructions.
- [ ] A real client/server test passes text, single/multiple/repeated images,
      and concurrent requests, with both-profile preprocessing correctness and
      clearly scoped real-model generation evidence.
- [ ] Tests prove unchanged token/grid/placeholder semantics, correct cache
      identities and ownership, no duplicate preprocessing, and the intended
      vision-encoder path. Full repository and integration suites pass.
- [ ] A reproducible paired serving measurement includes transport/copy costs,
      cold/warm cache behavior, latency, throughput, event-loop impact, memory,
      and failures; the report states whether the measured benefit justifies
      adoption and preserves all historical certification limitations.
- [ ] An installable adapter/client example and exact launch instructions make
      the supported path usable without reading the seam prototype; remaining
      server/API limitations and unsupported flows are explicit.
