# C2: Build the PyO3/NumPy binding

## Goal

Expose C1's complete native batch operation as a minimal Python API whose large
outputs are NumPy-owned without a copy, whose metadata exactly matches the
pinned official processor contract, and whose ownership and failure lifetimes
are safe and testable.

## Scope

- Add a thin PyO3 binding that accepts a batch of structured conversations plus
  encoded image buffers and caller-owned RGB arrays in one Python call.
- Convert and validate Python inputs at the boundary, then run native batch
  processing with the GIL released and without a Python callback per visual.
- Expose the official conditional output set as C-contiguous NumPy arrays:
  `input_ids`, `attention_mask`, and `mm_token_type_ids` as `int64`;
  `pixel_values` as `float32`; and `image_grid_thw` as `int64` when images are
  present.
- Transfer the large native pixel allocation into NumPy without copying while
  preserving exact shapes and strides; keep metadata ownership equally clear
  and safe.
- Define typed Python exceptions for the stable core error categories and test
  input/output lifetimes, retained views, dropped processors/inputs, and every
  failure path for leaks, double frees, use-after-free, or partially returned
  outputs.

## Non-goals

Do not add Python callbacks, one-Rust-call-per-visual adapters, Torch ownership,
async scheduling policy, native parallelism, performance certification, video,
or vLLM integration.

## Acceptance Criteria

- [x] One Python call prepares heterogeneous multi-request batches, including
      the roadmap's one-image and 24-image shapes, without invoking Python once
      per visual.
- [x] Long-running native work executes with the GIL released; a concurrency
      regression proves another Python thread can make progress.
- [x] Every returned array has the official conditional presence, exact dtype,
      shape, C-contiguous strides, values, padding, and deterministic order.
- [x] The large `pixel_values` allocation crosses from Rust to NumPy with no
      data copy; tests establish allocation/data-pointer identity or equivalent
      ownership evidence.
- [x] Borrowed input buffers remain valid for the required duration and returned
      arrays remain valid after inputs and processor objects are dropped.
- [x] Invalid inputs and allocation/execution failures raise the mapped stable
      exception without leaks, double frees, use-after-free, partial outputs, or
      unreleased borrows/GIL state.
- [x] Wheel build/install smoke, focused binding tests, Phase B conformance, and
      the full repository correctness suite pass.

## Worklog

### 2026-08-02 — accepted after implementation and independent review

Implemented the installed `qwen_mm` batch API with a reusable `Processor`, an
official-array-only `PreparedBatch.arrays` mapping, separate complete A6
metadata, strict boundary validation, ten stable typed exception subclasses,
and NumPy-owned C-contiguous outputs. The complete C1 plan/execute operation
runs inside `Python::detach`; test-only instrumentation proves a Python worker
can observe the native execution window, while the production wheel proves the
instrumentation is absent. Exact one-image, 24-image, heterogeneous, failure,
lifetime, retained-view, raw-buffer, key/padding/stride, and zero-copy cases are
covered. The 24-image `pixel_values` C-order SHA-256 also matches the committed
golden exactly.

The implementation agent and two independent read-only reviewers found and
closed issues around exception pickling/module identity, conditional output-key
purity, category and precedence mapping, raw-array edge cases, bool-versus-int
validation, output conversion failures, resource preflight ordering, a leaked
diagnostic pointer, and the strength of the GIL/lifetime/value regressions. No
Kingdom peasant was used. The final API and test audits reported no actionable
blockers.

Validation passed with `make phase-c-binding-check`, which includes the full
repository checks, wheel build/install smoke, Phase B conformance, and focused
installed-wheel binding tests. Feature-specific strict Clippy, ignored embedded
NumPy unit tests, `git diff --check`, and a production-wheel NumPy `2.4.6`
installation were also verified. Media byte limits are preflighted before
foreign-buffer copies; aggregate text size is evaluated after fallible string

### 2026-08-02 — Python ownership and result surface selected

The binding will expose a reusable `Processor` and one structured
`prepare_batch` call. Python bytes, strings, and C-contiguous aligned
`uint8[H,W,3]` arrays are validated and copied into an owned Rust request graph
while the GIL is held; the entire native plan/execute operation then runs under
`Python::detach` with no borrowed Python memory or callback. Exact native
`Vec<i64>`/`Vec<f32>` destinations are transferred through rust-numpy's owned
base object and reshaped without copying. Adapter metadata is kept separate
from the official array mapping so exact output-key conformance is not diluted
by a private `_metadata` key.
