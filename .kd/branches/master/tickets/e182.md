# D1: Add native observability and publish profiles

## Goal

Make the complete structured-input-to-materialized-NumPy operation observable,
then use the existing paired benchmark workloads to publish a ranked,
evidence-backed bottleneck list on ARM and x86. This ticket establishes the
measurement basis for D2 and D3; it does not optimize based on assumptions.

## Scope

- Add request- and media-scoped spans for planning, decode/color conversion,
  resize, normalization, patchification/layout, chat rendering/tokenization,
  destination execution, and the Python/NumPy binding boundary.
- Count native and Python calls at the stage boundaries so profiles expose
  accidental callbacks, duplicate processing, or unexpected fallback work.
- Count allocations, allocated/copied bytes, buffer lifetimes, peak transient
  live bytes, and retained final-output bytes without conflating the 432 MiB
  materialized result with scratch memory.
- Produce whole-operation flamegraphs or equivalent sampled profiles using the
  A5 workload contract, including `jpeg24_one_request`, `ragged24`,
  `jpeg1_offgrid`, both text cases, and `rgb24` in representative one-thread
  and production-thread configurations.
- Publish separate ARM and Linux x86 evidence with exact source revision,
  build mode, profile/model, workload, thread budget, profiler, commands, and
  host provenance, followed by a ranked bottleneck and allocation/copy list.
- Keep observability deterministic, testable, and either disabled or bounded
  in release timing so instrumentation does not silently become the workload.

## Non-goals

Do not add parallel execution, fusion, arenas, new output modes, video support,
or a certified speed claim. Candidate optimizations discovered here belong to
D2 or D3 and must cite the published evidence.

## Acceptance Criteria

- [ ] Every declared native and binding stage emits request/media-correlated
      spans with stable names, ordering, byte/shape counts, and success/error
      outcomes; tests cover text-only, encoded-image, raw-RGB, repeated-image,
      heterogeneous-batch, and failing requests.
- [ ] Allocation instrumentation distinguishes retained outputs from transient
      buffers and reports allocation count, copy count/bytes, live bytes, and
      peak transient live bytes; focused tests reconcile counters against known
      small workloads.
- [ ] Python-call counters prove the candidate batch path performs one public
      Python call and no callback per visual, and expose any unexpected
      candidate-path Hugging Face, Qwen VL Utils, Pillow, or TorchVision work.
- [ ] Whole-operation profiles are captured for the required core cases on a
      native ARM host and a native Linux x86 host under explicit equal thread
      budgets and current passing C3 conformance evidence.
- [ ] A versioned machine-readable profile summary plus readable report ranks
      time, allocation, copy, and buffer-lifetime bottlenecks separately for
      ARM and x86 and identifies the evidence that will justify D2/D3 work.
- [ ] Observability-disabled results remain exactly conformant for both
      profiles, and enabled observability neither changes outputs/errors nor
      introduces unbounded per-request memory.
- [ ] The full repository correctness suite and profile-artifact validation
      pass from a clean checkout.

### 2026-08-02 — implementation audit started

The current C2 boundary is one `Processor.prepare_batch()` call that parses and
owns Python inputs, releases the GIL for serial `plan_batch` plus
`execute_plan_into`, and transfers the output `Vec` allocations into NumPy
without a copy. The core has no opt-in observability/report type, and the Python
package has no `qwen_mm.benchmark:create_adapter` factory despite that factory
being the A5 harness's documented candidate entrypoint.

D1 will therefore add a deterministic, bounded observed execution surface
covering stable native and binding stages plus owned-buffer/copy accounting,
and add reproducible capture/report validation around the existing A5 workload
contract. This checkout is native macOS ARM; no native Linux x86 host is
available here, so x86 evidence will be left as an explicit required capture
gap rather than inferred from the committed emulated conformance artifacts.
