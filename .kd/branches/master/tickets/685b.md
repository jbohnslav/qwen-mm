# Define a pragmatic v0.1 performance release gate

## Goal

Separate a credible first still-image/text release from the stricter long-term
performance certification and the later video/vLLM production roadmap. Define
which measured D4 gaps genuinely block v0.1, which become disclosed
limitations, and which remain post-release optimization targets.

## Proposed v0.1 Scope

- CPU text and still-image preprocessing for the two pinned Qwen profiles.
- Python 3.11 wheel support on native macOS ARM and Linux x86.
- Encoded JPEG/PNG/WebP and caller-owned RGB remain correct, but performance
  claims may be narrower than functional support.
- No encoded video, vLLM adapter, production canary, arbitrary Hugging Face
  processor compatibility, or exhaustive A5 performance claim.

## Proposed Gate Split

### Hard v0.1 blockers

- Full declared image/text conformance, stable errors, exact public structure,
  ownership/lifetime checks, GIL release, and installed-wheel smoke pass on
  both target architectures.
- The headline encoded-image workloads remain statistically faster than
  official: selected single-thread encoded cases beat official, and image24
  plus ragged24 retain their `>2x` controlled-host result on ARM and x86.
- The processor-owned pool remains deterministic, bounded, configurable, and
  free of nested-runtime oversubscription. The default remains serial.
- Native transient allocations are leak-free, exclude a full additional
  float-CHW intermediate, and stay within an explicit production-derived
  absolute budget. Near-zero official RSS deltas do not define v0.1 readiness.
- Any workload advertised as faster must actually pass its speed gate. ARM raw
  RGB must either reach parity/faster or be excluded explicitly from the v0.1
  performance claim.
- Release mechanics are proven: license and package metadata, user-facing
  install/API/scope documentation, reproducible macOS ARM and Linux x86 wheels,
  clean-environment wheel tests, changelog/tag, and a publish dry run.

### Certification and post-v0.1 targets

- `E_8 >=0.6` remains the scaling target but is not a release blocker while t8
  is faster in absolute terms, the pool is opt-in/configurable, and equal-budget
  comparisons remain published.
- Candidate transient memory `<=0.5x` official remains a comparative
  optimization target for workloads with a stable positive denominator, not a
  release blocker for zero/near-zero RSS deltas.
- The slight x86 official-baseline `CV=0.053491` miss remains an evidence
  quality task; it does not override a candidate speed lower bound above `2x`.
- Broader raw-RGB, batch-memory, and scaling improvements remain tracked and
  must not be represented as already certified.

## Acceptance Criteria

- [ ] The King approves the v0.1 product scope and the distinction between
      functional support, advertised performance, and strict certification.
- [ ] Every one of the 15 measured D4 misses is classified as a hard blocker,
      disclosed limitation, or post-release optimization target with a reason.
- [ ] A stable absolute/native memory-safety gate replaces unstable small-case
      official-RSS ratios for v0.1 without hiding the original measured miss.
- [ ] The pre-release optimization budget and stop rule are explicit.
- [ ] Release-preparation tickets cover packaging, documentation, native wheel
      verification, tagging, and publishing independently of Phase E/F.

## Worklog

### 2026-08-26 — initial release-gate assessment

The current result is sufficient to argue for a deliberately narrow first
release, not for the roadmap's final video/vLLM production release. x86 passes
all 12 selected image speed gates. ARM passes every encoded-image and selected
batch speed gate but is `0.819x/0.815x` on raw RGB. Headline image24/ragged24
speedups are already `4.7x–6.4x` on ARM and `2.6x–3.6x` on x86.

The current `E_8` requirement measures internal scaling, not user-visible
speed versus official. It misses at roughly 51% on ARM and 26% on x86 even
though every selected t8 absolute speed gate passes. Because the public pool
defaults to serial and remains bounded/configurable, this is suitable as a
published optimization target rather than an automatic v0.1 blocker.

The relative memory failures mix real optimization opportunities with an
unstable denominator. Exact candidate native peaks across selected cases are
approximately 5–72 MB while retained outputs are approximately 19–453 MB; the
two extreme ratios arise when the official external-RSS delta is tens of
kilobytes or below 1 MB. v0.1 should enforce a production-derived absolute
native scratch limit, leak/lifetime checks, and the existing no-full-CHW rule,
while retaining the strict comparative ratio as a future certification target.

Repository inspection also shows that performance is not the only release
work. Version metadata and a wheel smoke exist, but the root README is still a
project overview rather than install/support documentation; no native release
CI, release tag, changelog, or visible license was found. Those are small,
bounded release-engineering tasks but should precede a public v0.1 artifact.
