# Run the bounded ARM optimization pass for v0.1

## Goal

Make one disciplined, profile-driven optimization pass over the weakest ARM
paths before v0.1, prioritizing the genuinely slower `rgb24/t1` path and
accepting safe, obvious transient-allocation wins. Completion is based on doing
the bounded pass well, not on forcing every original D4 ratio to pass.

## Scope

- Capture a current whole-operation ARM profile for raw RGB and rank planning,
  conversion, patchification, resize, allocation, and copy costs.
- Implement only low-risk changes justified by the profile and measure each in
  isolation. Raw-RGB single-thread latency is the primary target.
- Inspect the known ARM batch/single-image native peaks for easy buffer-lifetime
  or scratch-reuse wins, but do not optimize against near-zero official RSS
  denominators.
- Re-run full image conformance, installed-wheel checks, and the relevant
  compact ARM coordinates after every accepted change.
- Publish before/after results and any remaining ARM limitation for the v0.1
  support/performance statement.

## Non-goals

Do not weaken or relabel the original D4 evidence, add architecture-specific
semantic behavior, hide allocations, oversubscribe, or expand into encoded
video/vLLM. The old `>1.0x` speed and `<=0.5x` comparative-memory gates remain
strict-certification targets, but they are not this bounded pass's close
condition.

## Acceptance Criteria

- [x] A current ARM profile ranks the real raw-RGB costs and distinguishes CPU
      work from allocation/copy overhead before code changes are selected.
- [x] At least one profile-justified low-risk improvement is measured in
      isolation and accepted only if it repeatably improves the target without
      a correctness, encoded-image, text, or memory regression; if no such
      change exists, the investigation and rejected options are documented.
- [x] ARM raw RGB is either statistically at least at parity with official or
      is excluded explicitly from v0.1 performance claims while remaining
      functionally supported.
- [x] Candidate transients remain leak-free, bounded, fully inventoried, and
      free of a full additional float-CHW intermediate; before/after exact
      native peaks are published even when comparative ratios remain misses.
- [x] Full image conformance, installed-wheel checks, repository correctness,
      and relevant ARM evidence validation pass with exact provenance.

- [2026-08-26 10:07] [codex:e0b1df8a] — 2026-08-26 — quick current raw-RGB code/profile triage

  Ran one local instrumented `rgb24/t1` operation per profile against the working-tree native module (diagnostic only, not controlled certification). Qwen3-VL/Qwen3.5 total observed durations were 119.480/120.521 ms. Exclusive rankings were: `native.batch.plan` 57.128/58.058 ms; `native.media.normalize_patchify_layout` 35.568/35.897 ms; `binding.destination.allocate` 11.777/11.722 ms; `native.media.resize` 9.294/9.415 ms; `binding.parse_requests` 2.417/2.407 ms. Peak tracked transient bytes were 72,308,760 for both profiles.

  Static review ranks these candidates for isolated measurement:

  1. Cache-key/profile SHA work inside batch planning. `image_cache_key` re-hashes all 34.459 MiB of logical raw RGB, `ProfileRegistry::bundled()` is rebuilt in both planning and plan-identity validation, and the locked `sha2` dependency currently enables only `default/std`, not its ARM hardware `asm` backend. This best explains the dominant unclassified batch-plan time and is the first CPU experiment.
  2. Exact temporal duplication in `execute_image_patchify_plan_into`. Both profiles freeze `temporal_patch_size=2`, but the loop reloads and re-normalizes every pixel for both identical temporal copies. Computing once and copying the exact f32 patch block could remove duplicate conversion/division while remaining bit-exact.
  3. Raw input lifetime in the Python binding. The 36,132,888-byte `binding.owned_media` snapshot remains live until the complete operation returns even though `BatchPlan` owns prepared RGB after planning. Prepared RGB totals 36,175,872 bytes, so the 72,308,760-byte peak is essentially both full sets together. Consuming/dropping owned requests immediately after `plan_owned_requests` should roughly halve tracked transient peak without weakening the immutable Python snapshot.
  4. Reuse pic-scale plans/scratch for repeated geometries. `rgb24` has only three repeated source shapes, while `resize_pic_scale_u8` constructs a plan and allocates scratch per occurrence. Current resize time is only about 9.3-9.4 ms total, so this is lower priority than planning and patchification.

  Do not revisit already-rejected zero-copy writable-NumPy borrowing, the slower normalization LUT, or pic-scale `PreferSpeed`; each conflicts with prior snapshot, timing, or frozen-quality evidence. Destination zero-initialization is visible at about 11.7 ms, but avoiding it safely would require a broader `MaybeUninit` destination contract and is not an initial low-risk change.
