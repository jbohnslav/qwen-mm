# Phase C: Batch and Python parity release

## Goal

Turn the conformant single-request Rust image processor from Phase B into a
native heterogeneous batch operation, expose that operation through a safe
PyO3/NumPy boundary, and pass the complete pinned text/image compatibility
corpus for both supported profiles. Phase C is the first Python-facing parity
release; it establishes correctness and ownership semantics before profiling or
performance claims begin.

## Child Tickets

- C1 / `08a0` — implement the two-phase serial batch API.
- C2 / `9580` — build the PyO3/NumPy binding.
- C3 / `72e4` — pass and publish the full image conformance gate.

## Execution Shape

C1 starts from the closed A6, B1, and B7 contracts. C2 follows C1 so the Python
surface wraps a proven core ownership and capacity model. C3 follows C2 and the
closed A3 corpus so it validates the actual Python-facing release boundary. The
epic depends on all three children and is a completion roll-up, not executable
implementation work.

## Scope Boundaries

Phase C remains serial and correctness-first. Deterministic parallelism,
profile-driven fusion, performance certification, video support, and production
vLLM integration belong to Phases D through F. Benchmark results may be gathered
for diagnostics, but no speed claim is allowed before C3 closes.

## Acceptance Criteria

- [ ] C1 through C3 are closed with implementation and verification evidence in
      their worklogs.
- [ ] The Rust core exposes planning, caller-destination execution, and
      allocating batch APIs for heterogeneous requests with deterministic,
      atomic results.
- [ ] One Python call prepares a complete batch while the GIL is released and
      without a Python callback per visual; official arrays have exact public
      dtypes, shapes, strides, and safe ownership.
- [ ] Both frozen profiles pass the complete declared text/image corpus through
      the Python-facing path, including conditional keys and stable error
      categories, and the first conformance report is published reproducibly.
- [ ] No Phase C artifact claims certified speed, parallelism, video parity, or
      production vLLM readiness; downstream work remains gated by the roadmap.
- [ ] The full repository correctness suite passes from a clean checkout, and
      `ROADMAP.md` is updated only if Phase C evidence changes downstream scope
      or dependencies.
