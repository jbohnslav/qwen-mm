# B5: Prove resize parity

## Goal

Select or implement Rust resize kernels from conformance evidence, not speed or
API convenience, and freeze the decision before decoding lands.

## Scope

- Build a stage harness that feeds identical source pixels and B3 destination
  geometry to candidate Rust kernels and the pinned Pillow image / TorchVision
  bicubic-antialias video references.
- Cover upsample, downsample, no-op, aligned/off-grid, aspect-ratio, min/max,
  high-frequency, edge, and color-channel cases on supported ARM and x86 hosts.
- Record dimensions and the full frozen diagnostics for each candidate; explain
  interpolation, coordinate, antialias, rounding, clamping, and color-domain
  behavior where results differ.
- Exact-pin and justify any selected dependency, or document and test the custom
  kernel if no maintained dependency passes.

## Non-goals

Do not choose a kernel because it benchmarks well, widen A1 tolerances, hide a
platform-specific failure, implement encoded-media decoding, or make an
end-to-end performance claim.

## Acceptance Criteria

- [x] The image corpus matches pinned Pillow dimensions with per-channel RGB8
      absolute error at most one for every pixel and reports all required
      diagnostics for any mismatch.
- [x] The video corpus matches pinned TorchVision bicubic+antialias in its
      `0..255` `float32` domain with `rtol=0`, `atol=1e-4`, even though video is
      not exposed by the Phase B API.
- [x] Cases cover no-op, representative up/down ratios, off-grid dimensions,
      factor/min/max boundaries, portrait/landscape inputs, impulses, ramps,
      checkerboards, and independent RGB channels.
- [x] Results are recorded separately for macOS ARM and Linux x86; a selected
      implementation passes both or an explicit implementation ticket/blocker
      is recorded instead of weakening the gate.
- [x] A tracked decision record names the evaluated candidates, exact versions,
      evidence, selected implementation, and consequences for B6 and Phase E.
- [x] The selected image/video resize entry points are covered by deterministic
      stage tests and can consume B3 plans without Python/Torch at runtime.
- [x] Core checks and the resize-stage conformance suite pass from a clean
      checkout.

## Worklog

### 2026-08-01 — evidence-driven kernel selection complete

- Built a deterministic 17-case Pillow 12.3.0 / TorchVision 0.28.0 stage
  oracle covering no-op, up/down, off-grid, factor/min/max, portrait/landscape,
  horizontal-only, vertical-only, padded non-noop stride, impulses, ramps,
  checkerboards, edges, noise, and independent RGB channels.
- Rejected exact-pinned `fast_image_resize=6.1.0`: six image and three video
  cases failed, with 10,049 and 114 values beyond the frozen bounds. It remains
  dev-only so the comparison is reproducible and is absent from the normal
  `qwen-mm-core` dependency tree.
- Selected in-tree kernels. The image kernel is explicitly documented as
  Pillow-tolerance-compatible rather than exact Pillow arithmetic: 825 of
  359,424 bytes differ, maximum error one, none beyond the bound. The
  source-faithful TorchVision video path is bit-identical on the corpus.
- Recorded authenticated native macOS ARM and Linux x86_64-under-QEMU reports.
  The report bodies match across hosts; Linux emulation and the Mac-captured
  oracle are explicit limitations, not performance or native-hardware claims.
- Independent Lord and kernel review caught and corrected misleading Pillow
  provenance, unchecked weight capacity, forged-plan/filter-window handling,
  report source staleness, prefix/NaN false passes, and missing one-axis/stride
  cases before acceptance.
